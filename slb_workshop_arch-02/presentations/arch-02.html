    ARCH-02 — Lifecycle, Governance & Standards

    Good architecture needs governance to match. This session is a design review — four problems you must decide before the platform scales, not a product tour.

    01 · ILM / retention strategy

    Long-term platform design starts with named classes — by value, cost, and compliance — not a pile of ILM JSON copied from the last cluster.

    • Policy first. Classes such as platform metrics, app logs, audit, and traces. Namespace can change retention of the same dataset (prod vs nonprod).
    • Mechanism second. Serverless uses DSL (data_retention). Hosted uses ILM tiers or, in 9.5+, DSL with frozen_after. Cover both; do not hardcode one.
    • Decide today. What data deserves different retention, and who owns the exception when a team wants longer.
    02 · Fleet-managed vs standalone

    An operating-model choice. Both paths store telemetry in Elasticsearch. They are not operationally interchangeable.

    • Fleet-managed Agent. Central policy, health, and versions from Kibana. Use where central governance is required. Trade-off: less collector flexibility.
    • Standalone / EDOT-native. Full OTel flexibility. Config lifecycle (version, approve, promote, audit) becomes the team’s problem on day one — or it is a snowflake.
    • Decide today. Who is allowed which path. Supported: EDOT SDKs + Managed OTLP or Agent Gateway. Unsupported: EDOT + APM Server OTLP.
    03 · ECS vs OTel semantic conventions

    Elastic donated ECS to OTel (2023) and is converging on SemConv. 9.5 ships the alignment dictionary — not one merged authoring schema.

    • Not every mismatch is a rename. Clean mappings, equivalent-but-renamed (trace.id / trace_id, message / body.text), translation-required, and a metrics data-model gap that aliases cannot fix.
    • Working proposal. OTel-native for new telemetry. ECS only while Fleet is the source of truth. Mixed authoring on one stream is prohibited.
    • Decide today. Default schema for the next three years, and where translation is allowed vs banned.
    04 · Ownership & reusable standards

    Central standards plus team autonomy inside guardrails. 200 engineers across three sites cannot run on tribal knowledge. Uncontrolled dataset creation is the fastest path back to five tools.

    • Taxonomy. <type>-<dataset>-<namespace>. Dataset is a signal shape, not one stream per microservice. Namespace = environment unless you write a different rule.
    • Split. Platform owns templates, classes, naming, and schema guardrails. Teams own instrumentation, approved collectors, and dashboards on standard fields. Extend via @custom — no mapping forks.
    • Decide today. Who may create a dataset, who approves a new field, and how fast the exception process is.
    Thesis — do not repeat the 5-tool mess

    SLB is consolidating 5+ tools into one platform. OTel / EDOT expands the governance surface; it does not shrink it. The APIs are not the hard part. Inconsistent streams, templates, pipelines, and schemas across workstreams are. Objective: controlled consistency. If you leave with concepts and no owners, you have not done the session.

    01 · Retention

    Policy first, mechanism second

    Do not define governance as “ILM settings.” Name classes, then map each class to a lever. A 7-day workshop retention is not a platform design.

    Data stream lifecycle (DSL)

    Serverless lever: data_retention on the stream. ILM APIs return 410 here — that is expected.

    Hosted 9.5+: frozen_after searchable snapshots are GA. DSL vs ILM is now a real choice, not a Serverless-only story.

    ILM + data tiers

    Hosted / self-managed: hot → warm → cold → frozen → delete. Restore SLAs for audit need frozen / searchable snapshots.

    If both ILM and DSL are attached, ILM wins unless you say otherwise. Do not attach both by accident.

    ClassWhy it existsServerless DSLHosted ILM mapping
    Platform metricsHigh volume, high query frequency7dhot → delete 7d
    Application logsIncident investigation + trend30d prod / 14d nonprodhot → warm 7d → delete 30d
    Audit / securityCompliance drives policy90d stand-in for 1y+hot → warm → cold → frozen → 365d
    Traces (sampled)Cost-sensitive at volume3dhot → delete 3d
    Do not copy Serverless templates onto hosted blindly

    Namespace can carry a different retention of the same dataset (logs-workshop.app-prod vs -nonprod). Unsanctioned streams such as logs-rogue.drilling-prod skip the contract — that is the failure mode, not a missing ILM JSON file.

    02 · Collection

    Fleet-managed vs standalone — an operating-model choice

    Both paths store telemetry in Elasticsearch. They are not operationally interchangeable. Architects decide who is allowed which path — do not re-argue Agent vs OTel (SRE-01 already covered that).

    Fleet-managed Elastic AgentStandalone / EDOT-native
    Best forShared platform collectors, regulated hosts, any fleet that must look the same tomorrowApp teams that need a vendor-neutral collector and custom processors
    Who owns configFleet policy in Kibana. Platform owns the integration allow-list and rollouts.The team. Git (or equivalent) version, approve, promote, audit — before first prod ship.
    Health & versionsVisible in Fleet. Drift is a Fleet problem.You build the inventory. Unmanaged binaries are invisible until they break ingest.
    FlexibilityIntegrations and Agent policy. Slower path for custom OTel processors.Full collector graph. That flexibility is why governance must exist on day one.
    Failure modePolicy sprawl — every team gets a one-off integration instead of a standard package.A snowflake collector. Switching later is allowed and not free (re-instrument, re-map, re-train).
    Who is allowed which path
    • Default to Fleet wherever central policy, health, or a regulated host is required.
    • EDOT-native is an exception, not a preference. Grant it by team type, not by whoever asked first.
    • If SLB allows the path, the config-governance model must exist before first prod ship — versioned config, approval, promotion, audit. Otherwise it is not a standard.
    • Record the decision: which team types are on EDOT-native on day one, and who reviews the next request.
    EDOT support boundary (do not re-litigate)
    • Supported: EDOT SDKs + Managed OTLP endpoint, or EDOT SDKs + Elastic Agent Gateway. This is the path for new EDOT work.
    • Unsupported: EDOT SDKs + APM Server OTLP. May function. Elastic will not support it if it breaks. Do not let a workstream pick this by accident.
    • SRE-01 already ran the operator lab. Architects only decide eligibility and the exception SLA — not the collector internals.
    03 · Schema

    ECS → OTel — Elastic is converging on the standard

    April 2023: Elastic donated ECS to OpenTelemetry and committed to converge with SemConv. That is a direction, not a single merge event. 9.5 is the first Stack release where that convergence is operational for architects.

    Why Elastic moved to OTel
    • Industry standard. Vendor-neutral SemConv + OTLP is how most new instrumentation ships. ECS alone was becoming a second dialect.
    • EDOT / Agent-as-collector. Elastic’s path for new app telemetry is OTel-native ingest (mapping_mode: otel), not “translate everything to classic ECS first.”
    • One destination, two histories. Fleet integrations and classic APM still emit ECS. New EDOT paths store OTel layout (resource.attributes.*, body.text, severity_text).
    What “unified” means in 9.5
    • Alignment dictionary ships. ECS 9.5.0 ↔ OTel SemConv 1.38.0 — identical, equivalent, related, metric, and non-applicable mappings are documented. See alignment overview.
    • Query bridges, not one schema. Passthrough fields and aliases let many OTel docs answer ECS-style queries (e.g. service.name). Compatibility is incomplete — not every field has an alias.
    • Still two authoring models. Convergence ≠ one field name at write time. Architects still pick a canonical model per stream.
    Four buckets — alignment docs are the dictionary, not the policy
    BucketExampleWhat breaks
    Identical / cleanMany resource attributes ↔ ECS field setsUsually nothing if you pick one and alias
    Equivalent, renamedtrace.id ↔ trace_id · message ↔ body.text · log.level ↔ severity_textDiscover, dashboards, alerting — the same incident is invisible across schemas
    Related / translation requiredSemantics overlap but are not identicalAliasing lies; you need a transform, not a field alias
    Metrics data-model gapOTel metrics (name, type, dimensions) ≠ ECS metric-like fieldsCannot be solved by renaming. Do not promise a global alias layer for metrics.
    OTel-native for new telemetryNew logs and traces use OTel fielding. Match Elastic’s direction — a three-year target-state decision.
    ECS only while Fleet is source of truthDo not rewrite those streams in place. Translation is a migration cost, not a standing dual-write.
    Mixed authoring on one streamOne stream does not accept both log.level and severity_text. Pick one model per dataset.
    9.5 makes governance harder to skip, not optional

    Passthrough and aliases reduce query pain — they do not erase dual schemas on disk. Alignment increases the need for a written standard. Decide the default now; do not wait for “full unification.”

    04 · Ownership

    Taxonomy, templates, and who may change what

    Central standards plus team autonomy inside guardrails. Uncontrolled dataset creation is the fastest path back to fragmentation.

    <type>-<dataset>-<namespace>   →   logs-workshop.app-prod
    PartMeaningWorking proposal
    typelogs / metrics / tracesNo other types without an exception
    datasetSignal shape or bounded contextNot one dataset per microservice. workshop.app, not svc-drilling-api-v3
    namespaceThe tenancy knobEnvironment (prod / nonprod). If you pick team or region instead, write it down. “prod”, “drilling”, “us-east”, “alice-test” in the same slot has no governance value.
    Central platform owns
    • Approved integrations, base component templates, shared ingest processors
    • Retention classes, lifecycle policies, namespace / dataset naming
    • Schema guardrails (ECS vs OTel policy), cross-team dashboards and SLO standards
    Domain teams own
    • Service instrumentation, OTel adoption, approved collector deploy (Fleet or EDOT)
    • Team dashboards on standard fields; service SLOs and team alerts
    • Limited custom attributes under policy; exception requests for new datasets / fields
    The only approved way to add a field

    Extend via @custom (example: logs-workshop.app@custom → slb.well_id). A team dashboard that needs a new field is an exception, not a local mapping fork.
